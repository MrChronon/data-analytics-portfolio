# Excel Data Quality & VBA: проверка начислений РКЦ

Практический кейс на основе тестового задания по проверке качества расчетной выгрузки расчетно-кассового центра (РКЦ) в Excel, восстановлению части пропущенных данных, реконструкции производных показателей и автоматизации свода дебиторской задолженности через VBA.

> Исходная рабочая книга содержит операционные данные, поэтому в публичный репозиторий не выкладывается. В кейсе опубликованы методика, агрегированные результаты и VBA-код без лицевых счетов и исходной выгрузки.

## Задача

В исходной книге находилась выгрузка по **3 990 лицевым счетам**. Требовалось:

1. выполнить набор Excel-задач на поиск, текстовые преобразования и агрегирование;
2. заполнить свод по индивидуальным и многоквартирным домам;
3. определить количество ошибок РКЦ, хотя само понятие ошибки в условии не было формализовано;
4. написать VBA-макрос, который по кнопке формирует список ЛС с положительной дебиторской задолженностью на конец периода.

Главная аналитическая часть кейса возникла именно из неоднозначности пункта про ошибки: необходимо было сначала восстановить бизнес-логику расчетов, а затем отделить арифметические ошибки от недостаточности первичных данных.

## Стек

`Microsoft Excel` · `INDEX/MATCH` · `COUNTIF / COUNTIFS` · `SUMIF` · `SUMPRODUCT` · `IF` · `Data Validation` · `VBA` · `Data Quality`

## Подход

### 1. Первичный контроль качества

Проверены:

- дубли по ЛС;
- пропуски по полям;
- допустимые диапазоны и знаки числовых значений;
- возможность однозначно восстановить расчетные зависимости.

Дубли по лицевым счетам отсутствовали. Пропуски были обнаружены в полях **«Тип строения»**, **«Тариф»** и **«Всего начислено по услуге»**.

### 2. Восстановление расчетной логики

Из данных были установлены две проверяемые зависимости:

```text
Начислено по услуге = Тариф × Количество человек
```

и

```text
Всего начислено по услуге = Начислено по услуге + Перерасчёт
```

По первой проверке найдено:

- **81 запись**, где расчет нельзя проверить из-за отсутствующего тарифа;
- **162 записи** с арифметическим расхождением.

По второй проверке:

- **30 записей** без результата «Всего начислено»;
- **66 записей** с заполненным, но неверным результатом.

Поле **«Сумма оплаты за услугу»** не использовалось как самостоятельный критерий ошибки. Из условия следующего задания следует, что это входная величина для движения задолженности:

```text
ДЗ на конец = ДЗ на начало + Всего начислено - Сумма оплаты
```

Поэтому знак или несовпадение оплаты с начислением сами по себе не доказывают наличие ошибки.

### 3. Ошибка считалась на уровне ЛС

Один лицевой счет мог одновременно нарушать несколько правил. Поэтому итоговый показатель задавался как булев признак:

```text
есть хотя бы одна проблема → проблемный ЛС
нет проблем → OK
```

При раздельном суммировании нарушений получилось **339 случаев**, но уникальных проблемных лицевых счетов оказалось **330**.

Это позволило избежать двойного учета одной и той же записи.

## Ключевые результаты исходной выгрузки

| Показатель | Значение |
|---|---:|
| Всего ЛС | **3 990** |
| Проблемных ЛС | **330** |
| ЛС без типа строения | **104** |
| Доля ЛС без типа строения | **2,61%** |
| Проблемных ЛС среди записей без типа | **85** |
| Доля этих записей среди всех проблемных ЛС | **25,76%** |

Несмотря на то что записи без типа строения составляли только **2,61% базы**, на них приходилось более четверти всех проблемных ЛС. Это стало отдельным сигналом о связи между неполнотой классификационных данных и общим качеством записи.

## Восстановление пропущенных данных

В записях, где тип строения был заполнен, обнаружилась детерминированная связь:

- `ИЖД → тариф 175`;
- `МКД → тариф 200`;
- исключений в заполненных данных не было.

Это позволило безопасно восстановить **23 из 104** пропущенных значений типа строения.

Гипотеза о восстановлении отсутствующего тарифа по количеству человек и начислению была отклонена. В проблемных строках не существовало устойчивой зависимости: одинаковые начисления встречались при разном количестве проживающих, а некоторые ненулевые количества людей сочетались с нулевыми начислениями.

Поэтому дальнейшее заполнение потребовало бы необоснованных предположений и не выполнялось.

## Реконструкция производных показателей

На отдельной копии данных было принято дополнительное допущение: первичные поля **«Тариф»**, **«Количество человек»** и **«Перерасчёт»** считаются корректными.

После этого производные показатели были рассчитаны заново:

```text
Начислено = Тариф × Количество человек
Всего начислено = Пересчитанное начисление + Перерасчёт
```

Результат:

| Этап | Проблемных ЛС |
|---|---:|
| Исходная выгрузка | **330** |
| После восстановления и реконструкции | **81** |
| Снижение количества проблемных записей | **75,5%** |

Оставшиеся **81 ЛС** содержат пропуск первичного тарифа. Эти записи нельзя достоверно восстановить только средствами имеющейся выгрузки без внешнего источника или дополнительного бизнес-правила.

```mermaid
flowchart LR
    A[Исходная выгрузка<br/>3990 ЛС] --> B[Профилирование качества]
    B --> C[330 проблемных ЛС]
    C --> D[Проверка связи<br/>тип строения ↔ тариф]
    D --> E[Восстановлено 23 типа]
    E --> F[Реконструкция начислений]
    F --> G[81 ЛС остаются<br/>без достаточных первичных данных]
```

## VBA-автоматизация

В третьей части задания реализованы два макроса:

- свод по исходным данным;
- свод по реконструированным данным.

Макрос проходит по строкам, рассчитывает:

```text
ДЗ на конец = E + J - K
```

и выводит только ЛС с положительной задолженностью.

Для реконструированной версии добавлена проверка `IsNumeric`, чтобы строки с недостаточными первичными данными не интерпретировались как нулевые значения и не приводили к `Type mismatch`.

Полный VBA-код вынесен в [`vba/macros.bas`](./vba/macros.bas).
