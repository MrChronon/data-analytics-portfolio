# Аналитическая записка

## Задача 1

В части 1.3 обозначения типа населенного пункта (`г.`, `дер.`, `пос.` и др.) намеренно сохранены. Это позволяет не терять информацию о типе населенного пункта, если в исходных данных встречаются не только города.

По той же причине в названиях улиц сохранены обозначения `ул.`, `наб.`, `пер.` и т.п., а в номере дома - `д.`. Если потребуется стандартизация адресов с выделением только значений (`Москва`, `Большая`, `15`), формулы могут быть дополнительно доработаны.

## Задача 2

### 1. Первичный анализ данных

В выгрузке были обнаружены пропущенные значения и ошибки в расчетных показателях.

На первом этапе данные намеренно анализировались без восстановления пропусков по косвенно связанным признакам. Это позволило сохранить исходное состояние выгрузки РКЦ и показать расхождения между общими итоговыми показателями и значениями, которые можно распределить по заданным категориям.

Первичная проверка показала:

- дубли по лицевым счетам отсутствуют;
- поля «Населенный пункт», «ЛС», «ДЗ на начало по услуге», «Количество человек», «Начислено по услуге», «Перерасчет по услуге» и «Сумма оплаты за услугу» заполнены;
- пропуски присутствуют в полях «Тип строения», «Тариф» и «Всего начислено по услуге»;
- допустимость положительных, отрицательных и нулевых значений оценивалась с учетом предполагаемой бизнес-логики показателей.

### 2. Методика определения ошибок РКЦ

Для выявления ошибок были установлены две расчетные зависимости.

#### Начисление по услуге

```text
Начислено по услуге = Тариф × Количество человек
```

Выявлено:

- **81 запись**, для которой расчет невозможно проверить из-за отсутствующего тарифа;
- **162 записи** с арифметическим расхождением.

#### Всего начислено по услуге

```text
Всего начислено по услуге = Начислено по услуге + Перерасчет по услуге
```

Выявлено:

- **30 записей** с отсутствующим значением «Всего начислено»;
- **66 записей**, где заполненный результат не соответствует расчетной зависимости.

Итого по данному контролю: **96 проблемных записей**.

Поле «Сумма оплаты за услугу» не использовалось как самостоятельный критерий ошибки. Из условия задачи 3 следует, что оно является входной величиной при расчете дебиторской задолженности:

```text
ДЗ на конец = ДЗ на начало + Всего начислено - Сумма оплаты
```

Следовательно, положительные и отрицательные значения оплаты сами по себе не позволяют установить наличие ошибки без дополнительной бизнес-информации.

### 3. Принцип подсчета ошибок

Ошибка учитывалась на уровне лицевого счета как булев признак. Если по одному ЛС выявлено одно или несколько нарушений либо отсутствуют необходимые для расчета данные, такой ЛС считается проблемным один раз.

При раздельном суммировании всех нарушений получается **339 случаев**, тогда как количество уникальных проблемных ЛС составляет **330**.

### 4. Расхождения в исходных данных

Из-за отсутствующего значения «Тип строения» часть ЛС невозможно однозначно отнести к ИЖД или МКД.

Выявлено:

1. **104 ЛС** без указанного типа строения, или **2,61%** от общего числа.
2. ДЗ на начало периода по этим ЛС составляет **2 480 671 руб.**, или **2,80%** общего значения.
3. Текущие начисления составляют **41 375 руб.**, или **0,68%**.
4. Сумма перерасчетов составляет **-68 615 руб.**, или **2,83%** итогового значения по модулю.
5. Среди этих ЛС **85 являются проблемными**, что составляет **25,76% от всех 330 проблемных лицевых счетов**.

Несмотря на долю всего 2,61% от базы, записи с отсутствующим типом строения содержат более четверти всех выявленных проблемных ЛС. Это указывает на связь между неполнотой классификационных данных и общим качеством записей.

### 5. Восстановление пропущенных данных

Восстановление выполнялось на отдельной копии, исходная выгрузка не изменялась.

В записях с заполненным типом строения была обнаружена однозначная связь между типом и тарифом:

- ИЖД с тарифом, отличным от 175: **0**;
- МКД с тарифом, отличным от 200: **0**.

На основании этой зависимости удалось восстановить **23 из 104** пропущенных значений «Тип строения».

Дополнительно проверялась возможность восстановить отсутствующий тариф по полям «Количество человек» и «Начислено по услуге». Устойчивой зависимости обнаружено не было: одинаковые начисления встречаются при разном количестве проживающих, а в части строк начисление равно нулю при ненулевом количестве человек.

Поэтому дальнейшее восстановление тарифа по этим признакам не выполнялось.

После этого осталось **81 ЛС**, для которых отсутствуют тип строения и тариф. По имеющимся данным однозначно определить тип строения для этих записей невозможно.

### 6. Реконструкция расчетных показателей

На отдельной копии данных выполнен следующий уровень анализа.

Сделано допущение, что первичные данные в полях «Тариф», «Количество человек» и «Перерасчет по услуге» являются корректными.

На их основании заново рассчитаны производные показатели:

```text
Начислено по услуге = Тариф × Количество человек
Всего начислено по услуге = Пересчитанное начисление по услуге + Перерасчет
```

Таким образом были устранены выявленные арифметические ошибки в производных полях.

Невосстановленными остались **81 запись**, в которых отсутствует тариф. Для них невозможно однозначно рассчитать начисления без внешнего источника данных или дополнительных бизнес-правил.

Результаты реконструкции:

1. **81 ЛС** остается с неопределенным типом строения, или **2,03%** базы.
2. ДЗ на начало по этим ЛС составляет **1 929 089 руб.**, или **2,18%**.
3. Расхождение по текущим начислениям отсутствует: из-за отсутствующего тарифа начисления для этих 81 ЛС в реконструированном наборе не формировались.
4. Сумма перерасчетов по данным ЛС составляет **-53 754 руб.**, или **2,22%** итогового значения.
5. После реконструкции остается **81 проблемный ЛС**. Все оставшиеся проблемы связаны не с арифметическими ошибками, а с недостаточностью первичных данных.

В рамках принятых допущений восстановление однозначно определяемых атрибутов и реконструкция производных показателей позволяют сократить количество проблемных ЛС с **330 до 81**.

## Задача 3

Реализованы два VBA-макроса, запускаемых кнопкой «СВОД» и формирующих перечень ЛС с положительной дебиторской задолженностью на конец периода.

Используемая формула:

```text
ДЗ на конец = ДЗ на начало + Всего начислено - Сумма оплаты
```

Подготовлены два варианта:

- свод по исходным данным;
- свод по реконструированным данным.

Для реконструированной версии добавлена проверка числовых значений, чтобы строки с недостаточными первичными данными не интерпретировались как нулевые и не приводили к ошибке типа в VBA.
